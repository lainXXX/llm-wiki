# 规模阈值与档位行为

## 判据：非空白字符数

**不要用 `wc -w`。** 它按空白分词——一整段中文 ≈ 1 个"词"，于是"index ≤8k token"这种判据对中文语料永远成立，阈值形同废纸。用**非空白字符数**，并把"中文 1 字符 ≈ 1 token"当作**保守上界**直接对齐阈值。

`node <SKILL_DIR>/scripts/wiki_stats.js` 直接给结论。

| 档位 | 判据 | 检索策略 |
|------|------|---------|
| **S** | index ≤ **8k 字符** 且 页面 ≤100 | 直接 Read `wiki/index.md` 全文 + grep |
| **M** | index 8k–20k 字符 **或** 页面 100–300 | **不全量读 index**：分节按需读 + grep 优先；单次 query 读页 ≤8 |
| **L** | index >20k 字符 **或** 页面 >300 **或** 单次 query 需读 >15 页 | **只给指引，不实现**：告诉用户"这个库已超出本 skill 适用范围"，给出拆库 / 换检索工具两个选项。**拆库是 v4 的一级手段**（不再只是"逃生舱口"）——按知识空间拆成兄弟 instance，两边用跨库链接接上 |

阈值取保守值：低估上下文的代价是**静默的质量下降**，比多花点时间严重得多。

## 行为触发信号（比页数更可操作，agent 应主动提示）

- 最近 5 次 query 中 **≥2 次** grep 命中超过 50 条
- 某次 query 因为读页太多而超时/截断
- 单次 ingest 无法在 5 页上限内装下该源的重点（说明关联度已经太稠密）
- 命中 L 档 → 明确告知 + 给选项，不要硬跑

## 为什么没有本地检索（BM25/向量）

会审决定只实现 S + M，不引入外部检索依赖：小规模下 index + grep 足够，引入索引层会带来"索引与页面不同步"这一整类新故障，而它换来的收益要到 L 档才显现——而 L 档按设计就是"该拆库了"。

**换检索工具不是拆库的替代品，是另一条路**：如果库大是因为**同一个知识空间**积累得太多（不是词表装不下彼此），拆库帮不上忙——拆出去的两半仍然互相引用、仍然要一起查。那时该换检索工具，而不是硬拆。
